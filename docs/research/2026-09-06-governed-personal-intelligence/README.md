# Personal Intelligence as a Governed Digital State — Research Report

**Date:** 2026-09-06 · **Status:** research deliverable (no implementation decisions are binding until a `/spec` freezes them) · **Companion files:** [`landscape.md`](landscape.md) (project-by-project evaluations and capability matrix), [`poc.md`](poc.md) (POC design and evaluation protocol), [`council-review.md`](council-review.md) (seven-member adversarial review of this report, verdict, and an addendum on Google's Open Knowledge Format), [`conflict-count.md`](conflict-count.md) (evidence file closing the council's first kill criterion).

> Guiding question: can a person's accumulated principles, rules, lessons, decisions and reasoning patterns become a persistent, governed, versioned, continuously evolving intelligence layer that many AI agents consult and execute consistently — _one evolving intelligence, many agents, many projects, many sessions_ — while preserving consistency, provenance, governance and low context cost?

The short answer, argued below: **yes, and about two thirds of it already exists in composable form.** The nation-state analogy is a useful _design lens_ but a poor _implementation blueprint_. What is genuinely missing is small: a rule schema carrying authority level, lifecycle status, scope and evidence; a compiler from one canonical rule source into every agent's native format plus deterministic enforcers; and an evidence-counted promotion ledger from lessons to rules to principles. Everything else — storage, versioning, review, distribution, retrieval, enforcement — should be delegated to Git, structured Markdown, hooks, linters, and the agents' own context-loading mechanisms.

---

## 1. Problem definition

### 1.1 The symptom

Every new project and every new AI session starts from zero. The person's hard-won ways of working (prefer deterministic scripts to repeated LLM calls; tests before implementation; hexagonal boundaries; never weaken a test to make it pass) are re-explained, re-discovered, or silently violated. Lessons learned in project A are not available in project B. Rules exist as prose that each agent re-interprets differently, and the prose is paid for in tokens on every turn whether or not it applies.

### 1.2 The actual problem (not "a memory database")

Stated as requirements, independent of any analogy:

| #   | Requirement                                                                                                                                                   | Why it is hard                                                                                                                          |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| R1  | **Stratified authority.** Some statements (principles) must outrank others (rules), which outrank project conventions, which outrank a session's suggestions. | Agents treat every instruction in context as roughly equal; authority must be _structurally_ encoded, not asserted in prose.            |
| R2  | **Governed evolution.** Rules change, but through a procedure with review, evidence, versioning and rollback; the most fundamental layer requires a human.    | An agent that can rewrite its own principles will rationalize its way out of them; an agent that cannot propose changes never improves. |
| R3  | **Evidence-linked learning.** Experience → lesson → candidate rule → validated rule → principle, with provenance and repeated evidence at each promotion.     | Most memory systems store _facts_; almost none model _norms with lifecycle and evidence_.                                               |
| R4  | **Consistent multi-agent execution.** Claude Code, Codex, local agents, CI jobs and MCP clients must apply the _same_ rules.                                  | Every agent has its own context-file format and enforcement surface.                                                                    |
| R5  | **Hierarchical scope.** Personal → organization → project → repository, with inheritance, specialization, override and restriction.                           | Config-layering is a solved problem; layering _norms_ with precedence semantics is not standardized for agents.                         |
| R6  | **Minimum-context retrieval.** Load only what the current decision needs; enforce deterministically where possible so the LLM never sees the rule at all.     | Static instruction dumps are the dominant cost; the cheapest rule is one enforced by a hook.                                            |
| R7  | **Provenance and history.** Every rule and lesson can be traced to the experience that produced it and the review that approved it.                           | Requires append-only records and links, not a mutable "current state" file.                                                             |
| R8  | **Local-first, syncable.** Works offline on one machine; converges with a central copy.                                                                       | Text merge vs CRDT tradeoffs; but the volume is tiny.                                                                                   |
| R9  | **Conflict handling.** Detect contradictions between rules; resolve by precedence, scope, recency, or human judgement.                                        | Full static conflict detection over natural-language rules is impossible; it is tractable for the machine-checkable subset.             |

### 1.3 What it is _not_

- Not a vector database of chat transcripts. Episodic recall is one input to learning, not the product.
- Not a new agent framework. The agents already exist; the layer must be consumed by them as they are.
- Not a knowledge graph for its own sake. Graph structure earns its place only where edges are queried (dependencies, supersession, evidence links).
- Not an autonomous self-rewriting system. Self-improvement is bounded by an amendment procedure.

### 1.4 License posture (user decision, 2026-09-06)

The layer is an **internal tool** used to build commercial software. It is never embedded in, linked into, or redistributed with a shipped product, and it is not served to third parties over a network. Under that posture, copyleft licenses on the tooling (GPL, AGPL, and for local use also BSL and SSPL) are **not a constraint**: AGPL's network clause binds only when a modified copy is offered to outside users, and GPL binds only on distribution. The only license rule that stays in force is the one about the _product's own dependency graph_, which belongs to the project's laws, not to this layer. Landscape verdicts therefore rank projects on architecture fit alone; license is recorded for information and would matter again only if the layer were ever packaged for customers.

## 2. Conceptual model

### 2.1 Three kinds of content, three different substrates

The single most consequential finding of this research is that the "intelligence layer" is not one thing. It holds three kinds of content with different change rates, authority, and retrieval patterns, and each wants a different substrate:

| Content class | Examples | Change rate | Authority | Best substrate | Knowledge-layer frontmatter standard | **Open Knowledge Format v0.2** (Google Cloud, Apache-2.0): `sources[]`, `generated`/`verified` with the `human:<id>` actor convention, `status`, `stale_after`, index and log files, attested computations | Apache-2.0 | Vendor-neutral, already specifies human-reviewed trust tiers and a decay term; adopted under the law schema, never instead of it. (v2) |
| Knowledge-layer tooling | **okf-agent-memory** (`okf` CLI + MCP server): validate, BM25 search, create/update with index and log bookkeeping, bootstrap | MIT | **User decision 2026-09-06.** Verified locally: builds from source, tests pass, `validate` exits 1 on a missing `type` and with `--strict` on a broken link, MCP handshake exposes six tools. Runs over `knowledge/` only, never over `laws/`, because its MCP tools include create/update and laws are PR-only. Keep files as the source of truth so it can be dropped without loss; re-check maintenance monthly (two commits, one author at adoption). (v2) |
| Retrieval |
| ------------------------------------------------------------------ | ------------------------------------------------------------------------------------ | ---------------- | --------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| **Norms** (constitution, laws, conventions) | "prefer deterministic artifacts"; "tests fail before implementation"; "no AGPL deps" | Rare, deliberate | High → stratified | Small structured Markdown files in Git, reviewed by PR, **compiled** into enforcers and per-agent context files | By scope + trigger; digest always, body on demand; enforcer at zero tokens |
| **Semantic knowledge** (descriptive facts, architecture, glossary) | "the umbrella chart stages subcharts"; "module X owns Y" | Moderate | Descriptive, trust-graded (`active` / `review-needed` / `superseded`) | Markdown topics with frontmatter + a root router (progressive disclosure) | Routed: index → map → topic → section |
| **Episodes / evidence** (what happened) | ledger entries, test results, decisions, corrections, rotations | Continuous | Low individually; high in aggregate | Append-only log (JSONL / ledger), folded into state; indexed for search | By query, never bulk-loaded |

Treating these as one store is the root error of "just use a memory database." Norms need review and compilation; facts need routing and trust status; episodes need append-only provenance and cheap aggregation.

### 2.2 The governance mapping, revised

| Governance concept                         | Personal-intelligence equivalent                                                                               | Keep?                                | Note                                                                                                                                                                                                  |
| ------------------------------------------ | -------------------------------------------------------------------------------------------------------------- | ------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| Laws                                       | Operational rules derived from principles, each with scope, status, and an **enforcer**                        | **Keep (load-bearing)**              | "A law with no enforcement is a suggestion" is the single most useful legal metaphor here.                                                                                                            |
| Government                                 | The agents and automation that apply the rules                                                                 | **Keep, but as an _enabling state_** | See §2.3. The government's product is _infrastructure_ (scripts, checkers, retrieval), not runtime interpretation.                                                                                    |
| Ministries / institutions                  | Specialized agents, skills, scripts, model-tier routing                                                        | Keep, loosely                        | Institutions here are _capabilities_, not org chart. Coercion is replaced by fail-closed automation.                                                                                    |

The analogy's strongest contribution is one idea it makes vivid: **a norm's authority is defined by how hard it is to change and by what enforces it, not by how strongly it is worded.**

### 2.3 The government must be an enabling state (_chính phủ kiến tạo_), self-learning and self-evolving

The user's refinement is the correct one, and it changes the architecture. A command-and-control government reads every law at every decision and adjudicates — that is the token-expensive, inconsistent, LLM-interpreted pattern this research is trying to escape. An enabling state instead:

1. **Builds the conditions for compliance rather than adjudicating it.** Its output is deterministic infrastructure: a hook that blocks the forbidden action, a checker that fails the build, a script that replaces the repeated LLM task, a retrieval index that surfaces the one relevant rule. Every law that can be given an enforcer gets one; the LLM is reserved for the judgement residue.
2. **Learns from its own execution.** Every session emits events (corrections, retries, failed gates, escalations). Those events are the raw material of lessons. The state consumes its own archive.
3. **Evolves itself within the constitution.** The government layer (tools, scripts, skills, routing tables) can be changed by agents _autonomously_ as long as the change passes the existing gates. Laws can be _proposed_ by agents but promoted only with evidence and human approval. The constitution changes only by human amendment. Autonomy decreases as authority increases.

This gives a clean three-speed system: infrastructure evolves daily, laws evolve monthly with evidence, the constitution evolves rarely with a human signature.

### 2.4 Authority levels and precedence

A minimal, complete precedence ladder (higher wins on conflict; lower may _sharpen_ but never _invert_ a higher layer):

```
L0  Safety / platform constraints          (outside the system; never overridable)
L1  Constitution     — personal principles, priority ladder            human-amended
L2  Laws             — operational rules with enforcers                 evidence-gated, human-approved
L3  Org / team norms — scoped specializations of laws                   org-approved
L4  Project rules    — conventions, architecture manifest, tiers        project-approved (may be agent-proposed)
L5  Repo / local     — path-scoped conventions, machine-local settings  agent-changeable
L6  Session          — the user's current instruction, task file        ephemeral
```

Resolution rules, in order: (1) a higher level wins; (2) at the same level, narrower scope wins (path-scoped over global); (3) at the same level and scope, the higher `authority` weight wins, where `authority` is an explicit field on the record set at approval (`core | standard | provisional`) and independent of whether the rule has an enforcer; (4) otherwise, most recently approved wins and the conflict is logged as a lesson. _v2 change (council amendment 3):_ the v1 text made "has an enforcer" the tie-break, which conflated the enforcement mechanism with deliberative authority and let a trivially scripted convention outrank a considered judgement law. Enforcement and authority are now two fields. **Gate on this whole ladder (council kill criterion 1):** before a precedence resolver is written, count the real cross-level conflicts in this repo's history where plain conjunction (every check must pass) gave the wrong answer; fewer than three by 2026-10-04 means the resolver is machinery for an absent problem and the checker package is the unit of reuse instead. **Result (2026-09-06, [`conflict-count.md`](conflict-count.md)): three hard collisions and three pre-emptive precedence clauses found, every one resolved at authoring time by a human writing an explicit clause, none at runtime. Decision: precedence is compile-time.** Overlapping laws must declare `overrides:` / `supersedes_in_scope:` / `layers_on:` and the compiler fails closed on an undeclared overlap; the ladder validates declarations (tighten, never loosen) and orders prose; **no runtime resolver is built**; enforcers compose by conjunction.

This is the same shape as existing authority hierarchies in industry (platform > developer > user > guideline in the OpenAI Model Spec; managed > user > project > local in Claude Code's settings), applied to a person's own norms rather than to a vendor's.

## 3. An existing partial instance: CLAUDART audited against the requirements

This repository is itself an attempt at the problem, scoped to one project at a time. Auditing it honestly is the cheapest way to see what the missing layer is, because everything it already does need not be built.

| Requirement                 | What CLAUDART already has                                                                                                                                                                                                                                    | Gap                                                                                                                                                                         |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| R1 stratified authority     | `rules/constitution.md` (priority ladder + 16 golden rules, always imported) above domain rules; domain rules loaded on trigger with a binding digest; task/spec files below. `constitution-check.sh` forbids duplicating the constitution into lower rules. | No machine-readable authority level on a rule; precedence is stated in prose.                                                                                               |
| R2 governed evolution       | `/learn` promotes recurring behavior into rules; rules "stay user-gated"; spec executors "never edit rules mid-loop"; standing approval model for missions.                                                                                                  | No version/status/since fields on rules; no proposal state distinct from approved; no rollback beyond git.                                                                  |
| R3 evidence-linked learning | NOTES `→ graduate:` flags; JOURNAL decision/pivot grep in `/learn`; LEDGER evidence anatomy; knowledge `status` lifecycle (`active`/`review-needed`/`superseded`/`retired`) with `sources`/`verify`.                                                         | Evidence is not _counted_; a rule does not point at the lessons that produced it; promotion criteria ("repeated 2+ times") are judged by the agent, not tallied.            |
| R4 multi-agent consistency  | Codex mirror (`.codex/guidelines/` byte-identical twins), AGENTS.md at root, skills, `/backup`/`/restore`.                                                                                                                                                   | Mirror is maintained by hand; no compile step; no Cursor/Copilot/Gemini targets; no MCP surface.                                                                            |
| R5 hierarchical scope       | `paths:` frontmatter on rules; subdirectory conventions; `install.sh --upgrade` and `INTEGRATE.md` distribute the template layer into projects and preserve local customizations.                                                                            | Only two layers (template → project). No personal layer above projects; no org layer; lessons flow _down_ via upgrade but never _up_ from projects into the personal layer. |
| R6 minimum context          | Auto-import budget enforced (200 lines); trigger + digest pattern; knowledge progressive disclosure (index → map → topic → section); tier routing; every MUST in graph rules tagged `⟦enforcer⟧` or `⟦judgement⟧` (D29).                                     | Only one hook (`context-guard`); most laws are still LLM-interpreted prose; no per-rule cost accounting.                                                                    |
| R7 provenance               | LEDGER append-only with events, commands, output lines, revisions; `graph/events.jsonl` orchestrator-only writes; JOURNAL.                                                                                                                                   | JOURNAL/LEDGER are not indexed or queryable across projects.                                                                                                                |
| R8 local-first / sync       | Plain files in git; `/backup` bundles.                                                                                                                                                                                                                       | No cross-machine or cross-project sync of the personal layer as such.                                                                                                       |
| R9 conflict handling        | Constitution priority ladder; `constitution-check.sh` (duplication, import budget, enforcer map); `claudart-graph lint` for architecture graphs.                                                                                                             | No detection of contradictory rules beyond duplication; no static analysis of scope overlap.                                                                                |

**Verdict:** CLAUDART is a working _project-scoped_ digital state with a constitution, laws, courts (fail-closed checkers), archives (ledgers) and an amendment path (`/learn`). What it lacks is precisely the _personal_ layer above projects, machine-readable rule metadata, the compile-and-distribute step, and the evidence tally that turns "I think this recurs" into "this recurred 4 times across 3 projects." Those are the missing abstractions, and they are small.

## 4. Comparison with alternative abstractions

The nation-state is one of several available lenses. The research compared it against the candidates in the brief and against two academic frames that turned out to fit better.

| Abstraction                                                                                             | What it captures well                                                                                                                                                                                           | Where it misleads                                                                                                                                                                    | Verdict                                                                         |
| ------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------- |
| **Nation-state** (constitution / laws / government / courts / archives)                                 | Authority precedence; amendment friction; separation of "who writes" from "who executes" from "who judges"; archives as evidence                                                                                | Elections and legitimacy (there is one principal); sovereignty and coercion (agents cannot dissent; the real mechanism is deterministic enforcement); citizenship; foreign relations | **Teaching device**, not the formal model                                       |
| **Ostrom's IAD rule levels** (constitutional → collective-choice → operational; polycentric governance) | The same three-level ladder, verified in 25+ years of commons research, _without_ sovereignty or elections; "higher levels have wider scope and more resistance to change" is a precise statement of the design | Not software-native                                                                                                                                                                  | **Formal grounding** for the authority ladder                                   |
| **Normative multi-agent systems / electronic institutions**                                             | Specification (ISLANDER) separated from a runtime enforcer that sanctions (AMELI); constitutive vs regulative norms                                                                                             | Formal-logic authoring; 2000s tooling that never met git, CI or LLMs                                                                                                                 | Prior art for "institutions" and "courts"; take the separation, not the tooling |
| Agent memory (CoALA taxonomy)                                                                           | Episodic / semantic / procedural distinction                                                                                                                                                                    | Storage and recall only; no authority, no governance                                                                                                                                 | One layer of the system                                                         |
| Policy-as-code (OPA, Cedar)                                                                             | Deterministic, versioned, testable enforcement; bundles distribute hierarchical policy                                                                                                                          | Non-generative: no path from experience to policy                                                                                                                                    | The **enforcement half**                                                        |
| Case-based reasoning (retrieve / reuse / revise / retain)                                               | The most formal experience-reuse lifecycle                                                                                                                                                                      | Retains cases, not induced rules; automatic retention                                                                                                                                | Inspiration for the lesson stage                                                |
| Knowledge graph                                                                                         | Queryable relations (supersedes, derives-from, evidence)                                                                                                                                                        | A data structure, not a governance system                                                                                                                                            | An implementation detail, and a premature one                                   |
| Digital twin                                                                                            | Persistent identity across model swaps                                                                                                                                                                          | A twin mirrors state for simulation; this layer _governs behavior_                                                                                                                   | Misleading; drop                                                                |
| Personal operating system / personal AI infrastructure                                                  | Scheduling, resource, permission framing                                                                                                                                                                        | Undersells the normative half                                                                                                                                                        | Acceptable umbrella term, imprecise                                             |
| Versioned knowledge system                                                                              | History, branching, rollback                                                                                                                                                                                    | Flat; no authority or amendment                                                                                                                                                      | The substrate, not the concept                                                  |
| Second brain / exocortex                                                                                | Persistence of a person's notes                                                                                                                                                                                 | No execution, no norms; passive archives do not change behavior                                                                                                                      | Wrong function                                                                  |

**Name.** The literature has two near-matches: _governed agent memory_ (arXiv:2603.17787, the mechanics half) and _constitutional memory architecture_ (arXiv:2603.04740, the normative half; a single-author March 2026 proposal with a four-subject pilot). Neither covers both. This report uses **Governed Personal Intelligence** as the working name, defined as _a versioned, evidence-gated personal constitution executed as governed agent memory_. The novel part, and therefore the part worth naming, is the human-gated, evidence-linked amendment procedure; memory storage and sharing are comparatively solved. The user's refinement (an enabling, self-learning, self-evolving government) has no prior hit in the literature searched and is treated as an original synthesis; the developmental-state literature (state creates conditions rather than commanding outcomes) supplies vocabulary.

## 5. Landscape of existing open-source projects

Full evaluations, licenses and sources are in [`landscape.md`](landscape.md). The one-paragraph version per category:

- **Agent memory** (Mem0, Letta, Graphiti, LangMem, Cognee, MemOS, ReMe, claude-mem, mcp-memory-service, Basic Memory, PLUR, Statewave, research skill libraries): fact memory with vector or graph retrieval is commodity; bi-temporal validity exists in two projects; procedural memory as a first-class type exists in a handful; human-readable git-native storage exists in three. **No project models authority levels, a proposed → approved state machine, or evidence-linked rules.** Closest shapes: PLUR (YAML in git, cross-tool, MCP; verified) and Basic Memory (Markdown + SQLite index + MCP, Obsidian-compatible, more mature). With copyleft off the table (§1.4) Basic Memory is the stronger reference for the Markdown-plus-index shape and PLUR for the git-sync, cross-tool shape.
- **Versioned knowledge and local-first** (git + Markdown, MADR, log4brains, Jujutsu, Dolt, TerminusDB, XTDB, Oxigraph, CouchDB, Syncthing, CRDT engines): git plus a validated frontmatter schema plus a folded index is the floor and is sufficient at this scale; Dolt is the first database worth reaching for if query or structured merge ever bites; XTDB only for enforced bitemporality; CRDTs and app-sync services are not needed for async agent-to-file workflows.
- **Policy engines and enforcement** (OPA, Cedar, Cerbos, OpenFGA, Conftest, ast-grep, Semgrep, CUE, pre-commit, lefthook, Claude Code hooks and permissions, AGENTS.md, Ruler, rulesync): Cedar is the only engine with provable static conflict detection; ast-grep is the license-clean structural checker; Claude Code `PreToolUse` hooks and CI behind branch protection are the two non-bypassable enforcement points; Ruler and rulesync compile one prose source into every agent's format but **none emits hooks, permissions, policy bundles or lint packs, encodes precedence, or checks conflicts**.
- **Protocols**: MCP resources are the right primitive for a rules server (none adopted exists; roots are deprecated); MCP, A2A and ACP express no authority, versioning or audit semantics.

```
   COURTS  = precedence resolver + fail-closed checkers + PR review; judgement residue → human or fresh-context reviewer
   KNOWLEDGE (descriptive facts) sits beside LAWS with its own trust lifecycle and a routed index; it is consulted, never enforced.
```

Design commitments, each traceable to a finding:

1. **Norms, facts and episodes get different substrates** (§2.1). Norms are compiled; facts are routed; episodes are folded.
2. **Every law names its enforcer or declares itself judgement.** This is CLAUDART's D29 rule (every MUST tagged `⟦enforcer⟧` or `⟦judgement⟧`) generalized to the whole corpus. The compiler treats the two classes differently: enforceable laws become zero-token artifacts; judgement laws become prose with a digest.
3. **Precedence is forbid-overrides-permit with default deny for enforceable laws, concatenation for advisory prose.** A narrower scope may add or tighten, never loosen. A contradiction between enforceable rules is a compile error (Cedar-style analysis where the rule is expressed as policy; a scope-overlap check otherwise); a contradiction between prose rules is a lint warning routed to review.
4. **The compiler is the enabling state's product.** It runs on every change to the personal repo and on every project adoption or upgrade. Nothing hand-maintains a mirror.
5. **Workers never write the archive of record.** The orchestrator or the tooling appends events; lessons are extracted from events, not from an agent's self-report. This is CLAUDART's orchestrator-only `events.jsonl` rule and the delegation rule that worker reports are claims.
6. **Promotion is tallied, proposed, and human-merged.** Thresholds are data (distinct projects, distinct sessions, recency), the proposal is a PR with evidence attached, and the constitution accepts proposals only from a human.
7. **Autonomy decreases as authority increases.** Tooling and project conventions evolve autonomously within the laws; laws evolve by evidence plus approval; the constitution by amendment.
8. **Nothing promotes itself, and nothing entrenches itself silently** (v2, from the council review). Promotion and retirement are one artifact shipped together: every law carries a decay term independent of usage evidence (`stale_after`, from OKF), because a working enforcer suppresses exactly the override and contradiction signals that would otherwise trigger its re-examination. The unit of success for the whole layer is **net reviewer-hours**, not tokens saved.

## 9. Integration model for Claude Code and other agents

**Claude Code** (already the richest surface):

- Constitution → `~/.claude/CLAUDE.md` at user scope for the personal layer, `.claude/CLAUDE.md` for the project layer; both are concatenated by Claude Code in the right order (user before project). The compiler emits both from one source.
- Laws with `judgement` → `.claude/rules/<law>.md` with `paths:` frontmatter so they load only when a matching file is touched; the digest goes into the trigger line in CLAUDE.md (the pattern CLAUDART already uses).
- Laws with an enforcer → `PreToolUse` / `PostToolUse` / `Stop` hooks registered in `settings.json` (exit 2 blocks), `permissions.deny` entries, or check scripts wired into `npm run check` and CI.
- Knowledge → `.claude/knowledge/INDEX.md` router (unchanged).
- Archives → LEDGER, JOURNAL, `graph/events.jsonl` (unchanged); a `SessionEnd` or `/checkpoint` step appends extracted lessons to the personal `lessons/` log with provenance pointers.
- Managed settings (`allowManagedHooksOnly`, `allowManagedPermissionRulesOnly`) are the org-layer enforcement point when an organization exists.

**Codex, Gemini CLI, Cursor, Copilot, Windsurf, Aider**: the compiler emits `AGENTS.md` (nearest-file-wins), which all of them read natively; Cursor additionally gets `.cursor/rules` with globs for path-scoped laws. Enforcers reach these agents through CI and pre-commit, since none exposes a hook API comparable to Claude Code's.

**CI/CD and scripts**: the enforcer set (check scripts, ast-grep packs, optional Conftest/Cedar bundles) runs behind branch protection. This is the boundary that catches every agent equally, including a human.

**Local LLM agents and MCP clients**: phase 2 exposes the compiled laws and the knowledge router as MCP resources (`law://<id>@<version>`, `knowledge://<topic>`), read-only. A local agent that cannot read files can still query the same layer. Roots are deprecated; scoping is carried in the resource URI.

**Offline and sync**: each machine clones the personal repo; a project pins a revision of it and moves the pin only in an explicit, reviewed upgrade (v2: no pull at session start); lessons flow upstream with `git push` at checkpoint. Nothing requires a server.

## 10. Knowledge lifecycle

The brief's ladder is adopted with three modifications from the research: promotion is _tallied_ (Rust stabilization reports, Wikipedia consensus), _every stage has a falsifier_ (a lesson that never recurs decays; a law whose evidence is invalidated is flagged), and _consolidation is selective_ (the cognitive-science finding that non-selective consolidation causes interference is the argument for a human gate).

| Stage               | Record                                                                                         | Who writes                                                                            | Gate to next stage                                                | Falsifier / decay                                                                             |
| ------------------- | ---------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- | ----------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| Experience          | ledger events, test results, corrections                                                       | orchestrator or tooling only                                                          | —                                                                 | —                                                                                             |
| Observation         | a NOTES or task entry flagged `→ graduate:`                                                    | the working agent                                                                     | reviewed at `/learn`, `/checkpoint`, or mission close             | dropped if not confirmed                                                                      |
| Lesson              | one JSONL line: summary, kind, project, session, provenance pointer, candidate law, confidence | `/learn` or `/checkpoint`                                                             | none; lessons are cheap and append-only                           | never deleted; superseded by a later lesson                                                   |
| Candidate rule      | `proposals/<id>.md` with the tally: distinct projects, sessions, last seen, conflicting laws   | the tally script, when a threshold is crossed (default ≥3 lessons across ≥2 projects) | PR review by the person                                           | closed proposal stays as history                                                              |
| Approved law        | `laws/<id>.md`, `status: approved`, `evidence:` links, `enforcer:` or `judgement`              | human merge                                                                           | —                                                                 | `status: deprecated` when evidence is invalidated or a successor supersedes it; never deleted |
| Repeated evidence   | the tally keeps counting after approval                                                        | script                                                                                | ≥N further confirmations and no contradicting lesson for a period | contradicting lessons reopen the law for review                                               |
| Potential principle | `proposals/constitution/<id>.md`                                                               | script proposes, **only a human can merge**                                           | amendment                                                         | —                                                                                             |

**v2 amendments (council):** (a) the lesson record carries a `signal` field (`enforcer-exit | failed-gate | user-correction | self-flag`) and no `confidence` field, which had no producer and no consumer; (b) the tally de-duplicates by provenance pointer and a candidate cannot cross the threshold on self-flags alone: at least one lesson must come from a deterministic signal; (c) the extraction step justifies its `candidate_law` retrieval-style against the existing law corpus (`matched_against:` lists the law ids it considered), and two independent extraction passes over the same correction are compared, so **classification-agreement rate** is measured from day one; (d) every law carries `stale_after` (OKF field, absolute instant, default approval + 12 months for enforced laws, + 6 months for judgement laws). Retirement is fail-soft and **tiered by `authority`** (decided 2026-09-06 under the Constitution's ladder, correctness and safety first): a `core` law (secrets, licenses, data loss, tenant isolation) never degrades below `block`, expiry only opens a queue item, because a safety enforcer must not silently stop protecting; a `standard` law degrades to `warn` after the grace period; a `provisional` law degrades to `warn` immediately at expiry. In every tier expiry emits an event and only a human deprecates. In detail: on expiry the law flips to `status: draft`, its enforcer keeps running but reports `warn` instead of blocking after a 30-day grace, and the review queue receives one item. A re-verification (`verified.by: human:<id>`) resets the clock; silence degrades a law and emits an event, it never deletes one. This answers the council's central finding without billing the reviewer for every correct law at once, and it never lets a wrong `standard` law block forever or a right `core` law vanish unnoticed.

Two flows the ladder does not show but the archive supports: **demotion** (a law whose enforcer keeps being legitimately overridden, or whose evidence is contradicted, is proposed for deprecation by the same tally) and **evidence invalidation** (when a source a law cites is superseded, the validator flags the law `review-needed`, the same mechanism the knowledge layer already uses).

Descriptive knowledge runs its own, already-existing lifecycle (`active` / `review-needed` / `superseded` / `retired` with `sources` or `verify`) and is never promoted into a law; the two streams cross only when a fact is the _evidence_ for a rule.

## 11. Governance and amendment model

**Three regimes, three speeds.**

| Regime                                                                              | What it governs                                    | Who may propose                                | Who may approve                                                             | Evidence required                                                            | Typical cadence |
| ----------------------------------------------------------------------------------- | -------------------------------------------------- | ---------------------------------------------- | --------------------------------------------------------------------------- | ---------------------------------------------------------------------------- | --------------- |
| **Regulation** (L4–L5: project and repo conventions, tooling, scripts, tier tables) | how the enabling state works                       | any agent                                      | passes existing gates (checks, tests, review where the project requires it) | the gate's own evidence                                                      | daily           |
| **Legislation** (L2–L3: laws and org norms)                                         | what agents must do                                | agents via the tally; humans directly          | a human, by PR merge                                                        | tally over the threshold, or an explicit human decision recorded as a lesson | monthly         |
| **Amendment** (L1: constitution)                                                    | how conflicts are ranked; what may never be traded | the tally may _propose_; only a human _writes_ | a human, by PR merge, with a written rationale in the decision record       | repeated legislation converging on the same principle                        | rarely          |

**Procedure for a law** (borrowed shape: Rust RFC, PEP, KEP):

1. A written proposal artifact exists (`proposals/<id>.md`), never a chat message. It carries the tally, the candidate text, the proposed `enforcer` (or the reason it must stay judgement), `derives_from`, `scope`, and every conflicting or overlapping existing law the resolver found.
2. A validator runs on the proposal: schema, id uniqueness, scope validity, precedence check against higher levels (a proposal that loosens a higher law is rejected mechanically), and a negative control proving the enforcer can fail.
3. A human reviews and merges. Merge flips `status: proposed → approved` and sets `since`.
4. The compiler runs and emits the enforcer and the prose to every target. A law is not in force until the compile succeeds.
5. Deprecation is `status: deprecated` plus `superseded_by`; the record is never deleted. Rollback is `git revert` of the merge, which the compiler propagates.

**Conflict resolution ("courts")** has three tiers, cheapest first: the precedence resolver (mechanical); fail-closed checkers, which are the constitution's legislation over itself (mechanical; CLAUDART's `constitution-check.sh` is the existing instance: no verbatim duplication of the constitution into laws, import budget, every MUST mapped to an enforcer); and human review at PR time for the judgement residue, optionally preceded by a fresh-context reviewer whose verdict is voided by any later change to the reviewed surface.

**Reviewer-capacity guard (v2, council amendment 5).** The maintenance loop is the one subsystem that had no enforcer. It gets one: a committed `budget.yaml` states the reviewer's hours per month; the tally rate-limits proposal generation to what that budget clears; every proposal carries `expires` (default 30 days) and an unmerged proposal closes with a `expired` disposition rather than lingering; **median proposal age** and **reviewer-hours** are first-class metrics; and a proposal or lesson queue older than the threshold fails a check in the same way a missing `enforcer` field does, so backlog is visible in CI rather than in a bored reviewer's silence.

**What agents may never do:** merge their own proposals; edit `constitution.md` or an approved law outside a proposal; weaken or delete an enforcer to pass; write to the archive of record from inside a worker. These four prohibitions are themselves enforceable laws (branch protection, CODEOWNERS on `constitution.md` and `laws/`, a checker that diffs enforcers against the approved set, the orchestrator-only write rule).

## 12. Context and cost optimization strategy

The objective is _retrieve the minimum intelligence necessary to make the current decision correctly_. The ranking below orders mechanisms by tokens-per-compliance, cheapest first; the strategy is to push every law as far up this list as its nature allows.

1. **Enforce, don't explain.** A law with a hook, a deny rule, a lint rule or a CI gate costs zero tokens per session and holds for every agent. This is the single largest lever and the one the surveyed memory systems miss entirely.
2. **Replace repeated LLM work with scripts.** The constitution's own rules 10 and 11; the tally is designed to detect exactly this pattern (a `kind: repeated-llm-task` lesson recurring is the trigger for a script proposal).
3. **Digest always, body on demand.** The compiler emits a one-line digest per law into the always-loaded file and the body into a path-scoped rule (Claude Code) or a skill; the agent pays for the body only when its trigger fires. CLAUDART's measured budget for the always-loaded layer is under 200 lines, enforced by a checker.
4. **Route facts progressively.** Root index → domain map → topic → section, with explicit read limits (at most two maps, three topics, two one-hop related topics).
5. **Stable prefix, dynamic edge.** Keep the compiled constitution and digests byte-stable across sessions so prompt caching works; put the session's dynamic state (task, delta) at the end.
6. **Compile bundles, don't query at runtime.** Statewave's insight without its server: the compile step produces a deterministic, token-bounded bundle per scope, so a session boots by reading one small artifact rather than assembling context.
7. **Fold episodes; never load them.** Ledgers and lessons are aggregated by scripts into counts and a proposal; the raw log is read only in slices and only when a diagnosis needs it.
8. **Deduplicate at compile time.** The constitution-duplication checker already exists; extend it to the compiled prose so the same sentence never appears at two levels.
9. **Tier routing.** Mechanical units run on the cheapest model; the digest-plus-enforcer design is what makes cheap sessions safe, because compliance no longer depends on the model reading and honoring prose.

Measure, don't assume: the POC's first metric is boot-context tokens before and after compilation, with a target of at least a 30% reduction, and its second is the share of violations caught deterministically.

## 13. Security and privacy model

- **Classification.** Three sensitivities on every record, reusing the knowledge layer's `sensitivity: public | internal | restricted`. Constitution and laws are usually `internal`; lessons may carry `restricted` provenance (client names, incident details) and are stored in a separate file that the compiler never copies into a project.
- **Data flow boundaries.** The personal repo is private. A project receives a _compiled_ subset (laws in scope, digests, enforcers), never the lessons log or restricted knowledge. Upstream flow (project → personal) carries lessons with provenance pointers, and `/backup`'s existing secret-scan gate runs on the way up.
- **Secrets.** Never in norms, lessons, or archives; the existing backup secret scan and a pre-commit secret scanner on the personal repo are the mechanical guard.
- **Integrity of the archive.** Append-only files, orchestrator-only writes, and branch protection on the personal repo; a checker fails if a ledger line was edited (hash chain optional, likely unnecessary for one principal).
- **Integrity of enforcement.** Enforcers are compiled from approved laws and diffed against the approved set in CI; an enforcer that drifted from its law is a failed check. Hooks are registered from committed `settings.json`, not local settings, so a project cannot silently disable a law; Claude Code managed settings (`allowManagedHooksOnly`) are the org-scale version.
- **Least privilege for agents.** Workers get briefs, not the repo; the spec folder is gitignored from worktrees so a worker physically cannot write the graph; MCP resources are read-only.
- **Privacy of episodes.** Lessons store summaries and pointers, not transcripts; transcript retention is the harness's concern and stays outside the layer.
- **Auditability.** Who proposed, who approved, which enforcer fired, and which law was in force at a given revision are all answerable from git history plus the ledger; this satisfies "who did what, to which resource, when, and whether it succeeded" without an audit service.
- **Supply chain.** The compiled artifacts shipped into project repos are the layer's own files (Markdown, shell, YAML rules) and carry no third-party license. Tooling licenses are unconstrained per §1.4. The license check in the enforcer set governs the _products'_ dependency graphs, not the tooling.

## 17. Answers to the research questions

**A. What is this problem called?** The mechanics half is _governed agent memory_; the normative half is a _constitutional memory architecture_; the formal grounding is Ostrom's three rule levels (constitutional, collective-choice, operational). This report calls the whole **Governed Personal Intelligence**: a versioned, evidence-gated personal constitution executed as governed agent memory. Adjacent industry terms are policy-as-code (the enforcement half) and context engineering (the delivery half).

**B. Is it already solved?** No. Storage, retrieval, sharing and deterministic enforcement are each solved separately. No project or paper combines stratified authority, a human-gated proposed-to-approved lifecycle, evidence-linked promotion, and consistent multi-agent execution; the closest attempt is an unvalidated 2026 proposal. This repository is itself the closest working instance, at project scope.

**C. What combination is sufficient?** Git + Markdown + validated frontmatter for norms and knowledge; append-only JSONL for episodes; Claude Code rules, hooks, permissions and skills plus AGENTS.md for delivery; ast-grep, check scripts and CI for enforcement; Cedar only if authorization-shaped rules appear; MCP resources later for non-file agents.

**D. What is genuinely missing?** Three small things: a law schema with level, status, scope, enforcer and evidence; a compiler that resolves precedence, checks conflicts, and emits both prose and enforcers for every agent; and a lesson log with a promotion tally that produces proposals a human merges.

**E. Conceptual architecture?** §7: three content classes on three substrates, a compiler as the enabling state's product, an orchestrator-only archive, a tallied parliament, and courts that are mostly checkers.

**F. Minimum POC?** [`poc.md`](poc.md): one schema, one log, one script family, one adoption command, two projects, four weeks, five falsifiable hypotheses.

**G. What should not be built?** A memory database, a vector or graph store, a rule DSL, a sync service, a custom agent framework, an MCP server before the file path is proven, an LLM judge in the compliance path, and any autonomous promotion of rules.

## 18. Review status (2026-09-06)

This report was put through the repo's `/council` process after it was written; the full verdict is in [`council-review.md`](council-review.md). The council found the design worth building and one structural defect: the lifecycle promotes but has no working retirement path, because a working enforcer suppresses exactly the override and contradiction signals §10 relies on to demote a law, and the single human reviewer is the binding constraint that every proposed fix presses on. Twelve anchored amendments are proposed, four of which the council would not ship without: a decay term in the law schema shipped in the same commit as the schema; a reviewer-capacity guard shipped with it; splitting `enforcer` from an independent authority-weight field in §2.4; and deleting the `confidence` field from the lesson record. The council's upgrade to the idea is symmetry: _nothing promotes itself, and nothing entrenches itself silently_, with net reviewer-hours replacing tokens saved as the unit of success. The highest-value open input is a count of real cross-level rule conflicts in this repo's history; zero would mean the precedence engine is machinery for an absent problem. **Applied in v2 (2026-09-06):** §2.4 (authority field, conflict-count gate), §7 commitment 8 (symmetry), §8 (OKF + okf-agent-memory by user decision), §9 and §15 (pin, no session-start pull), §10 (`stale_after`, `signal`, no `confidence`, provenance dedup, classification-agreement), §11 (capacity guard), §15 steps 1–3 (retirement + capacity in one commit; external gate), §16 (cost marked unsized), and `poc.md` (schema, lesson record, metrics, H6, blinded H4). **Decided 2026-09-06 (user delegated the choice to whatever is best long-term and correct):** expiry is fail-soft tiered by `authority` (`core` never degrades below block; `standard` and `provisional` degrade to warn), and precedence is compile-time declaration checking, not a runtime resolver, on the evidence in [`conflict-count.md`](conflict-count.md). The addendum also records that Google's Open Knowledge Format v0.2 (Apache-2.0) already standardizes `verified.by: human:<id>` trust tiers, `stale_after`, and attested computations with a deterministic checker, and should be adopted as the frontmatter standard for the knowledge layer and reused on laws.
